1.1 控制基础

1.1.1 控制原理

学习目标

这一节，我们从 基础知识、控制流程、小结 三个方面来学习。

基础知识

简介

1	k8s集群通过 master角色主机 和 node角色主机 实现集群的环境搭建，所有的资源对象都是以pod为单元进行管理的。pod内部都是一个个相互关联的 容器对象。这些容器对象是来源于镜像仓库的镜像文件创建出来的。也就是说，k8s主要有 控制层面和数据层面来组成：
2	控制层面
3		API Server - 提供数据的注册和监视各种资源对象的功能
4		Scheduler - 将资源对象调度到合适的节点中。
5		Controller - 大量控制功能的集合,与API Server结合起来完成控制层面操作。
6	数据层面
7		Etcd - 提供各种数据的存储

节点资源管理

1k8s集群中的所有资源对象都是
2	- 通过 master角色主机上的各种组件进行统一管理，
3	- 基于node角色上的kubelet组件实现信息的交流。
4	- pod内部的应用对象
5		- 基于CRI让应用本身是运行在容器内部。
6		- 基于CSI实现各种持久化数据的保存。
7		- 基于CNI实现多个pod应用程序之间的通信交流。

资源访问

1对于k8s集群应用来说，所有的程序应用都是
2	- 运行在 Pod资源对象里面，
3	- 借助于service资源对象向外提供服务访问。
4	- 借助于各种存储资源对象实现数据的可持久化
5	- 借助于各种配置资源对象实现配置属性、敏感信息的管理操作
6	- k8s所有资源的操作必须具备相应的资源操作权限

控制流程

数据形态

1在Kubernetes集群中，一切的应用服务都是以各种资源对象来进行管理的，这些资源对象的创建流程：
2    首先：根据业务应用架构的分析，确定我们要使用的资源对象(Kubernetes中的)
3    其次：使用描述性语言，编写资源对象的定义文件
4    再次：基于资源对象定义文件进行对象初始化，形成资源对象。
5
6也就是说，在kubernetes中，资源对象有两种形态：
7	文件形态 - 编写出来的资源对象文件，有大量属性组成。
8	对象形态 - 基于资源对象文件初始化后出来的应用对象。

流程解读

1API Server 从某种层面上来说，它仅仅是一个数据库的接口，只不过
2	- 它支持对资源数据条目的 watch/notify 的功能，
3	- 它对于数据存储的格式进行了限制定制，也就是说，只能接收固定格式的数据规范。
4	
5	如果我们仅仅将相关对象的属性信息插入到 APIServer上，就相当于我们做企业规划的时候，准备为某个项目配置多少资源，而这个时候，这些资源是没有到位的，无法进行项目运行的。而kube-controller-manager就相当于企业的创始人，根据APIServer上的规划，通过招人、拉投资等方式，将一个个的具体对象落地。
6	
7示例：
8	比如每一个Service，就是一个Service对象的定义，同时它还代表了每个节点上iptables或ipvs规则，而这些节点上的规则，是由kube-controller-manager结合 kube-proxy来负责进行落地

pod管理

1	每一个Pod，就是一个应用程序的定义，同时它还代表了每个节点上资源的限制，而这些节点上的应用程序，是由kube-controller-manager 结合 kubelet来负责进行落地。
2	资源在创建的时候，一般会由Scheduler调度到合适的Node节点上。这个时候，kubeServer在各个节点上的客户端kubelet组件，如果发现调度的节点是本地，那么会在本地节点将对应的资源进行落地，同时负责各个节点上的与APIServer相关的资源对象的监视功能。
3	
4	注意，kubelet只负责单个节点上的Pod管理和调度。一旦我们需要对pod进行扩容缩容，涉及到了跨节点的资源调度，kubelet是做不到的。对于这些更高层级的应用资源调度，我们只能通过构建在 k8s 核心基础资源对象之上的控制资源来实现。

资源管理

资源状态

管理流程

 11 用户向 APIserver中插入一个应用资源的数据形态
 2	- 这个数据形态中定义了该资源对象的 "期望"状态，
 3	- 数据经由 APIserver 保存到 ETCD 中。
 42 kube-controller-manager 中的各种控制器会监视 Apiserver上与自己相关的资源对象的变动
 5	比如 Service Controller只负责Service资源的控制，Pod Controller只负责Pod资源的控制等。
 63 一旦APIServer中的资源对象发生变动，对应的Controller执行相关的配置代码，到对应的node节点上运行
 7	- 该资源对象会在当前节点上，按照用户的"期望"进行运行
 8	- 这些实体对象的运行状态我们称为 "实际状态"
 9	- 即，控制器的作用就是确保 "期望状态" 与 "实际状态" 相一致
104 Controller将这些实际的资源对象状态，通过APIServer存储到ETCD的同一个数据条目的status的字段中
115 资源对象在运行过程中，Controller 会循环的方式向 APIServer 监控 spec 和 status 的值是否一致
12	- 如果两个状态不一致，那么就指挥node节点的资源进行修改，保证 两个状态一致
13	- 状态一致后，通过APIServer同步更新当前资源对象在ETCD上的数据

对象解读

管理器

1	对于k8s场景中的应用任务来说，这些任务彼此之间主要存在 部署、扩容、缩容、更新、回滚等。虽然我基于pod的方式实现了应用任务的部署功能操作，但是对于我们自主式的pod来说，它并不能实现其他的几种任务。
2	而这显然 距 k8s的核心功能 是有一定的距离的，因此，在k8s集群的核心功能之上，有一群非常重要的组件，这些组件就是用于对pod实现所谓的任务编排功能，这些组件我们统统将其称为 -- 控制器。

控制器分类

 1对于控制器来说，他有很多种类:
 2	副本控制器(Replicas Controller):
 3		负责在节点中对各种资源对象进行增删改查等动态管理。
 4    节点控制器(Node Controller): 
 5    	负责在节点出现故障时进行通知和响应
 6    任务控制器(Job controller): 
 7    	监测代表一次性任务的 Job 对象，然后创建 Pods 来运行这些任务直至完成
 8    端点控制器(Endpoints Controller): 
 9    	填充端点(Endpoints)对象(即加入 Service 与 Pod)
10    权限控制器(Service Account & Token Controllers): 
11    	为新的命名空间创建默认帐户和 API 访问令牌
12    等等

资源对象

1控制器主要存在的几个部分：
2	应用部署部分 - Deployment、RC、RS、DaemonSet、Statefulset、Job、CronJob、等
3	服务访问部分 - Service、Ingress、Endpoint等
4	数据存储部分 - PV、PVC、SC、Configmap、Secrets等
5	安全管理部分 - SA、Token、Role等

控制器 vs Pod

1控制器主要是通过管理pod来实现任务的编排效果，那么控制器是通过什么机制找到pod的呢？
2	- 标签 或者 标签选择器

1.2.1 标签基础

学习目标

这一节，我们从 标签定位、命令实践、小结 三个方面来学习。

基础知识

简介

1	Kubernetes通过标签来管理对应或者相关联的各种资源对象，Lable是kubernetes中的核心概念之一。
1创建：	Lable通常在资源对象定义时确定，也可以在对象创建后动态添加或者删除
2本质：	lable本质上是一个key/value键值对，其中key与value由用户自己指定
3注意：
4	key的命名：由"字母、数字、_、.、-"这五类组成,只能以字符或数字作为开头和结尾。
5	标签名称不能多于63个字符
1作用：	
2	一个资源对象可以定义多个Lable，同一个Lable也可以关联多个资源对象上去
3	通过对Lable的管理从而达到对同Lable的资源进行分组管理(分配、调度、配置、部署等)。

操作方法

1方法1：资源清单方法
2    在特定的属性后面按照指定方式增加内容即可，格式如下：
3        labels:
4          key: value
5    注意：
6    	labels 是 一个复数格式。
 1方法2： 命令行方法
 2    查看标签：kubectl get pods -l label_name=label_value
 3        参数：
 4            -l 就是指定标签条件，获取指定资源对象，=表示匹配，!= 表示不匹配
 5            如果后面的选择标签有多个的话，使用逗号隔开
 6            如果针对标签的值进行范围过滤的话，可以使用如下格式：
 7            -l "label_name in|notin (value1, value2, value3, ...)"
 8    增加标签：kubectl label 资源类型 资源名称 label_name=label_value
 9        参数：
10            同时增加多个标签，只需要在后面多写几个就可以了，使用空格隔开
11            默认情况下，已存在的标签是不能修改的，使用 --overwrite=true 表示强制覆盖
12            label_name=label_value样式写成 label_name- ，表示删除label

1.2.2 标签选择器

学习目标

这一节，我们从 属性解读、简单实践、小结 三个方面来学习。

基础知识

简介

1	Lablel附加到Kubernetes集群中的各种资源对象上，目的就是对这些资源对象进行分组管理，而分组管理的核心就是：Lablel Selector。
2
3	Lablel Selector跟Label一样，不能单独定义，必须附加在一些资源对象的定义文件上。一般附加在RC和Service等控制器资源对象文件中。

表达式

1基础Label Selector表达式
2
3等式：
4    name = nginx 					匹配所有具有标签 name = nginx 的资源对象
5    name != nginx					匹配所有不具有标签 name = nginx 的资源对象
6集合：
7    env in (dev, test) 				匹配所有具有标签 env = dev 或者 env = test 的资源对象
8    name not in (frontend)  		匹配所有不具有标签 name = frontend 的资源对象
1扩展匹配Label Selector表达式
2
3匹配标签：
4    matchLabels:
5      name: nginx
6匹配表达式：
7    matchExpressions:
8      - {key: name, operator: NotIn, values: [frontend]}

RS ReplicaSet 维持 Pod 副本数 基于集合选择器 手动更新 无 共享 被 Deployment 管理
Deployment Deployment 无状态应用部署 管理 ReplicaSet 滚动更新/重建 无 共享 Web 服务、API
Job Job 一次性任务 运行到完成 不支持 无 临时/共享 批处理、数据处理
CronJob CronJob 定时任务 按计划创建 Job 不支持 无 临时/共享 定时备份、报表
DaemonSet DaemonSet 每节点一个 Pod 节点亲和 滚动更新 无 本地/共享 日志采集、监控
StatefulSet StatefulSet 有状态应用 有序创建/删除 滚动更新 稳定 独立持久化 数据库、缓存

1.3.1 RC&RS

学习目标

这一节，我们从 属性解读、简单实践、小结 三个方面来学习。

属性解读

简介

 1	Replication Controller（RC），是kubernetes系统中的核心概念之一。RC是Kubernetes集群实现Pod资源对象自动化管理的基础。
 2
 3简单来说，RC其实是定义了一个期望的场景，RC有以下特点：
 41、组成：定义了Pod副本的期望状态：包括数量，筛选标签和模板
 5	Pod期待的副本数量(replicas).
 6	永远筛选目标Pod的标签选择器(Label Selector)
 7	Pod数量不满足预期值，自动创建Pod时候用到的模板(template)
 82、意义：自动监控Pod运行的副本数目符合预期，保证Pod高可用的核心组件，常用于Pod的生命周期管理
 9
10	RC在kubernetes的早期kubernetes v1.2版本就被RS(ReplicaSet)替代了，但是RC目前仍然能够正常使用，因为RC的核心功能不仅仅是RS的核心，也是Deployment资源对象的核心。
11	RC 和 RS 的区别仅仅是资源对象名称和标签选择器不一样而已。

2	如果Pod数量大于RC定义的期望值，那么就杀死一些Pod
3	如果Pod数量小于RC定义的期望值，那么就创建一些Pod
4所以：通过RC资源对象，Kubernetes实现了业务应用集群的高可用性，大大减少了人工干预，提高了管理的自动化。
5拓展：

1.4.2 HPA实践

学习目标

基础知识

简介

1	对于 Kubernetes，Metrics API 提供了一组基本的指标，以支持自动伸缩和类似的用例。 该 API 提供有关节点和 Pod 的资源使用情况的信息， 包括 CPU 和内存的指标。如果将 Metrics API 部署到集群中， 那么 Kubernetes API 的客户端就可以查询这些信息，并且可以使用 Kubernetes 的访问控制机制来管理权限。
2
3	HorizontalPodAutoscaler (HPA) 和 VerticalPodAutoscaler (VPA) 使用 metrics API 中的数据调整工作负载副本和资源，以满足客户需求。水平(Horizontal)扩缩意味着对增加的负载的响应是部署更多的 Pods。 垂直(Vertical)扩缩扩缩意味着将更多资源分配给已经为工作负载运行的 Pod。

 8  maxReplicas <integer>					# 必选字段，扩容最大值

10  metrics      <[]Object> 				# 以什么指标监控
11  - type: Resource						# 监控的类型
12    resource:  <Object>						# 资源对象的属性
13      name: <string>					# 必选字段，监视资源名称，可以是cpu和mem
14      target:	<Object>				# 必选字段，资源目标值
15        type: <string>					# 必选字段，值的类型，
16        averageValue: <string>				# 普通目标数据值
17	averageUtilization  <integer>			# 百分比目标数据值
18  behavior:
19    scaleDown:  <Object>				# 缩容行为
20      stabilizationWindowSeconds: 90			# 扩缩容的基本时间范围，0-3600，默认300

 21  maxReplicas: 10              # 最大副本数
 22  
 23  # ==================== 扩缩容行为 ====================
 24  behavior:                    # Kubernetes 1.18+
 25    scaleDown:                 # 缩容行为
 26      stabilizationWindowSeconds: 300  # 稳定窗口：300 秒内选择最高建议值
 27      policies:
 28      - type: Percent          # 策略类型：Percent（百分比）或 Pods（绝对值）
 29        value: 50              # 每次最多缩容 50%
 30        periodSeconds: 15      # 15 秒内
 31      - type: Pods
 32        value: 2               # 或每次最多缩容 2 个 Pod
 33        periodSeconds: 60      # 60 秒内
 34      selectPolicy: Min        # 选择策略：Min（最小）、Max（最大）、Disabled（禁用）
 35    
 36    scaleUp:                   # 扩容行为
 37      stabilizationWindowSeconds: 0    # 立即扩容
 38      policies:
 39      - type: Percent
 40        value: 100             # 每次最多扩容 100%（翻倍）
 41        periodSeconds: 15
 42      - type: Pods
 43        value: 4               # 或每次最多扩容 4 个 Pod
 44        periodSeconds: 15
 45      selectPolicy: Max        # 选择最激进的策略
 46  
 47  # ==================== 指标配置 ====================
 48  metrics:
 49  
 50  # 1. Resource 指标（CPU、内存）
 51  - type: Resource
 52    resource:
 53      name: cpu                # cpu 或 memory
 54      target:
 55        type: Utilization      # Utilization（利用率）或 AverageValue（平均值）
 56        averageUtilization: 70 # 目标：平均 CPU 利用率 70%
 57# 计算方式:
 58# 1. 获取每个 Pod 的 CPU 使用率 = 实际使用 / requests.cpu
 59# 2. 计算所有 Pod 的平均利用率
 60# 3. 期望副本数 = ceil[当前副本数 × (当前平均利用率 / 70%)]
 61
 62# 示例:
 63#   当前 3 个 Pod，平均 CPU 利用率 90%
 64#   期望副本数 = ceil[3 × (90% / 70%)] = ceil[3.86] = 4
 65#   → 扩容到 4 个 Pod
 66  - type: Resource
 67    resource:
 68      name: memory
 69      target:
 70        type: AverageValue     # 使用平均值而非利用率
 71        averageValue: 500Mi    # 目标：每个 Pod 平均使用 500Mi
 72# 计算方式:
 73# 期望副本数 = ceil[总 CPU 使用量 / 500m]
 74# 注意：
 75# 内存扩缩容需谨慎，因为：
 76#   1. 内存不能像 CPU 一样节流
 77#   2. 内存泄漏会导致持续扩容
 78#   3. 缩容可能导致 OOM
 79# 建议：主要用 CPU，内存作为辅助指标
 80

 82  - type: Pods
 83    pods:
 84      metric:
 85        name: http_requests_per_second  # 自定义指标名称
 86      target:
 87        type: AverageValue
 88        averageValue: "1000"   # 目标：每个 Pod 每秒 1000 个请求

 99      target:
100        type: Value
