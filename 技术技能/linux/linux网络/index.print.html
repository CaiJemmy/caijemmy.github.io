虚拟网络设备

veth 对

veth（Virtual Ethernet Device） 是 Linux 内核提供的一种虚拟网络设备，总是成对出现：

  • 一端在宿主机，通常命名为 vethxxxx
  • 另一端在容器的 network namespace 中，通常命名为 eth0
  • 这对设备像一根虚拟的网线，将两个网络命名空间连接起来

veth 对的创建和连接过程

手动创建 veth 对的步骤：

 1# 1. 创建 veth 对（一端叫 veth0，另一端叫 peer0）
 2sudo ip link add veth0 type veth peer name peer0
 3
 4# 2. 查看创建的网络设备
 5ip link show | grep veth
 6
 7# 3. 创建一个新的网络命名空间（模拟容器）
 8sudo ip netns add testns
 9
10# 4. 将 peer0 移动到新的命名空间
11sudo ip link set peer0 netns testns
12
13# 5. 在宿主机中配置 veth0
14sudo ip addr add 10.0.0.1/24 dev veth0
15sudo ip link set veth0 up
16
17# 6. 在新的命名空间中配置 peer0（现在它是容器的 eth0）
18sudo ip netns exec testns ip addr add 10.0.0.2/24 dev peer0
19sudo ip netns exec testns ip link set peer0 up
20sudo ip netns exec testns ip link set lo up
21
22# 7. 验证连接
23ping -c 2 10.0.0.2

Docker 容器的实际创建过程：

当 Docker 创建一个容器时：

1# Docker 内部执行的类似命令：
2# 1. 创建 veth 对
3ip link add veth123456 type veth peer name eth0
4
5# 2. 将 eth0 移动到容器的 network namespace
6ip link set eth0 netns <container-pid>
7
8# 3. 将 veth123456 连接到 docker0 网桥
9brctl addif docker0 veth123456

删除宿主机 vethxxx 的影响

删除宿主机端的 vethxxx 会发生：

  1. 立即断开连接：

    1# 删除宿主机端的 veth 设备
2sudo ip link delete veth123456
    • 容器内的 eth0 会立即变成 NO-CARRIER 状态
    • 网络连接完全中断

  2. 容器内的表现：

    1# 在容器内查看网络状态
2ip link show eth0
3# 输出：eth0: <NO-CARRIER,BROADCAST,MULTICAST,UP> ...

  3. 恢复方法：

    • 重启容器：Docker 会自动重建 veth 对
    • 手动重建：需要重新创建 veth 对并重新连接

重要特性：

  • veth 对是双向连接的
  • 删除任何一端，另一端都会失效
  • 但另一端不会自动删除，只是变为不可用状态

多 veth 连接问题分析

问题 1：一个 eth0 连接多个 vethxxx？

答案：技术上可以，但不推荐也不常见

1# 理论上可以创建多个 veth 对连接到同一个命名空间
2sudo ip link add veth1 type veth peer name eth1
3sudo ip link add veth2 type veth peer name eth2
4sudo ip link set eth1 netns testns
5sudo ip link set eth2 netns testns
6
7# 在容器内会有 eth1 和 eth2 两个接口

但 Docker 的标准做法是：

  • 每个容器默认只有一个 eth0
  • 如果需要多个网络接口，使用 --network 参数： 
    1docker run --network=bridge --network=my-network ...

问题 2：宿主机多个 vethxxx 连接到容器？

答案：可以，这就是多网卡容器的实现方式

 1# Docker 创建多网络容器
 2docker network create net1
 3docker network create net2
 4
 5# 容器连接到多个网络
 6docker run -d --name multi-net \
 7  --network=bridge \
 8  --network=net1 \
 9  --network=net2 \
10  nginx
11
12# 查看结果
13docker exec multi-net ip link show
14# 会有：eth0@ifxxx, eth1@ifyyy, eth2@ifzzz 等多个接口

每个网络连接都会创建一对 veth：

  • 宿主机：vethA → 容器：eth0（默认 bridge）
  • 宿主机：vethB → 容器：eth1（net1）
  • 宿主机：vethC → 容器：eth2（net2）

01 LVS工作模式

LVS（Linux Virtual Server）是Linux内核级别的负载均衡解决方案，有三种主要工作模式：

1. NAT模式（Network Address Translation）

工作原理：

  • Director Server（调度器）接收客户端请求
  • 修改请求包的目标IP为Real Server IP
  • Real Server处理后，响应包发回Director
  • Director修改源IP为VIP，返回给客户端

特点：

  • Real Server可使用任何操作系统
  • Real Server只需配置Director为网关
  • 节省公网IP（只需Director有公网IP）
  • Director成为性能瓶颈（请求和响应都经过）
  • 支持端口映射

适用场景：
小规模集群（10-20台），Real Server在私网

2. DR模式（Direct Routing，直接路由）

工作原理：

  • Director接收请求，修改MAC地址为Real Server MAC
  • Real Server处理后，直接返回给客户端（不经过Director）
  • Real Server配置VIP在lo接口（抑制ARP）

特点：

  • 性能最高（响应不经过Director）
  • Director不是瓶颈
  • 支持大规模集群
  • Real Server必须与Director在同一网段
  • 不支持端口映射
  • Real Server需要抑制ARP响应

适用场景：
大规模高性能集群，最常用模式

关键配置：

1# Real Server需要配置（抑制ARP）
2echo 1 > /proc/sys/net/ipv4/conf/lo/arp_ignore
3echo 2 > /proc/sys/net/ipv4/conf/lo/arp_announce
4echo 1 > /proc/sys/net/ipv4/conf/all/arp_ignore
5echo 2 > /proc/sys/net/ipv4/conf/all/arp_announce
6
7# lo接口配置VIP
8ifconfig lo:0 VIP netmask 255.255.255.255

3. TUN模式（IP Tunneling，IP隧道）

工作原理：

  • Director将请求包封装在新的IP包中（IP隧道）
  • Real Server解封装后处理请求
  • Real Server直接返回响应给客户端

特点：

  • Real Server可跨地域部署（不受网段限制）
  • 响应不经过Director
  • 适合跨机房负载均衡
  • Real Server需要支持IP隧道
  • 不支持端口映射
  • 配置复杂

适用场景：
跨地域、跨机房的大规模集群

四种调度算法

LVS支持10种调度算法，常用的有：

静态算法：

  • RR（Round Robin）：轮询，平均分配
  • WRR（Weighted RR）：加权轮询，按权重分配
  • DH（Destination Hashing）：目标地址哈希
  • SH（Source Hashing）：源地址哈希

动态算法：

  • LC（Least Connections）：最少连接，分配给连接数最少的服务器
  • WLC（Weighted LC）：加权最少连接（默认算法）
  • SED（Shortest Expected Delay）：最短期望延迟
  • NQ（Never Queue）：永不排队
  • LBLC：基于本地的最少连接
  • LBLCR：基于本地的带复制功能的最少连接

02 DR模式实验

DR 模式的关键是：

  • Director 和 Real Server 必须处于同一个二层广播域；
  • VIP 同时配置在 Director 和 Real Server 上；
  • Real Server 必须避免对 VIP 的 ARP 请求进行响应；
  • Director 只修改目标 MAC，不修改 IP 和端口；
  • Real Server 的响应绕过 Director，直接返回客户端。

为什么配置到 lo 接口？

DR 模式中，Real Server 需要接收目标IP为 VIP 的数据包。因此，Real Server 必须认为 VIP 是本机地址。

将 VIP 配置在回环接口上，可以让 Real Server接收目标IP为 VIP 的报文，同时避免把 VIP作为正常接口地址直接暴露在二层网络中。

 5

参数含义

arp_ignore = 1

只在目标IP配置于接收ARP请求的接口上时响应ARP。

这样，Real Server 不会通过物理网卡抢答 VIP 的ARP请求。

arp_announce = 2

发送ARP请求时，尽量使用最合适的接口地址作为源IP，减少多网卡环境下的ARP混乱。

路由器相关疑问

路由器的每个端口上是否有网卡

疑问：路由器端口上配IP地址，就能实现数据包的封装转发，那么路由器的每个端口上是否都有一张网卡？

解答：路由器端口本质上就是一种特殊的网卡（网络接口卡），只是在叫法、形态和功能上有所区别。

路由器端口的本质

1路由器端口 = 网络接口 (Network Interface)
2           = 物理层 + 数据链路层功能
3           = 类似于网卡的硬件模块

从硬件角度看：

  • 路由器的每个端口都有独立的物理层芯片（PHY芯片）
  • 每个端口都有独立的MAC地址
  • 每个端口都有独立的数据链路层处理能力
  • 每个端口可以配置独立的IP地址

从功能角度看：

  • 路由器端口 ≈ 服务器上的网卡
  • 只是路由器有多个端口，而服务器通常只有1-2个网卡

Netfilter 是什么？（定义与定位）

Netfilter 是 Linux 内核中实现网络数据包过滤、地址转换（NAT）、连接跟踪（conntrack）、包修改等功能的 框架（Framework），不是用户直接操作的命令或工具。

  • 它是内核子系统（位于网络协议栈中），自 Linux 2.4 内核起成为标准组件，由 Rusty Russell 等人主导设计。
  • 它提供可扩展的钩子函数（hook points），允许内核模块（如 iptables 后端、nftables、xt_conntrack）在数据包穿越协议栈的关键路径上注册回调函数，实现策略干预。
  • 本质：Linux 网络栈的“策略注入点”，是所有 Linux 防火墙、NAT、负载均衡（如 IPVS）、容器网络（如 Docker、CNI）的底层基石。

类比理解：Netfilter ≈ “交通检查站的预留岗亭位置”，而 iptables/nftables ≈ “在岗亭里执勤的交警”（用户空间策略配置工具）。

Netfilter 架构核心：5 个 Hook 点（钩子）

Netfilter 在 IPv4 协议栈中定义了 5 个预设的 hook 点（IPv6、ARP、DECnet 等也有对应版本），数据包按固定顺序经过这些点。每个 hook 是一个函数指针链表，可挂载多个规则模块。

Hook 名称 触发时机（数据包流向） 典型用途 是否可修改包内容
NF_INET_PRE_ROUTING 数据包刚进入网络栈，尚未进行路由决策（即不知是发给本机还是转发） • DNAT（目标地址转换）
• conntrack 初始化（首次见到新连接）		 ✅ 是
NF_INET_LOCAL_IN 数据包目的地是本机（路由后），即将交给上层协议（如 TCP/UDP） • 主机防火墙（INPUT 链）
• 限速、封禁 IP		 ✅ 是
NF_INET_FORWARD 数据包需转发给其他主机（非本机，且 ip_forward=1） • 转发防火墙（FORWARD 链）
• 网关/NAT 设备策略		 ✅ 是
NF_INET_LOCAL_OUT 本机主动发出的数据包，尚未路由（如 curl http://example.com） • 主机防火墙（OUTPUT 链）
• SNAT（源地址转换，较少在此做）		 ✅ 是
NF_INET_POST_ROUTING 数据包即将离开本机（路由已完成，确定出口设备），最后修改机会 • SNAT（最常用位置）
• 修改 TOS、TTL、出口 MAC（如 mangle）		 ✅ 是

关键规律：

  • 所有 “进入本机”的包：PRE_ROUTING → LOCAL_IN
  • 所有 “转发的包”：PRE_ROUTING → FORWARD → POST_ROUTING
  • 所有 “本机发出的包”：LOCAL_OUT → POST_ROUTING

Netfilter 本身是框架，其能力依赖以下内核模块协同工作：

模块 功能说明 关联用户工具

iptables总体介绍

iptables 是 Linux 内核中 netfilter 框架的用户态管理工具，其“执行过程”本质上是指数据包在内核网络协议栈中经过 netfilter 钩子（hook）时，如何被 iptables 规则匹配与处理。需注意：iptables 命令本身不“执行”数据包处理，而是配置规则；真正的匹配与动作发生在内核 netfilter 的钩子点上。以下是清晰、准确的执行过程说明（基于 IPv4，标准内核流程）：

iptables 工具体系概述

iptables 是用户空间工具，通过 netlink 与内核 Netfilter 交互，管理 IPv4 规则；对应 IPv6 的工具为 ip6tables（已逐步被 nftables 统一替代）。

1、表（Tables）与链（Chains）

iptables 将规则组织在不同**表（table）**中，每张表专注一类功能，各表包含预定义链（chains）：

表名 主要用途 默认链（IPv4）
filter 包过滤（防火墙核心） INPUT、FORWARD、OUTPUT
nat 网络地址转换（DNAT/SNAT/MASQUERADE） PREROUTING、OUTPUT、POSTROUTING
mangle 修改数据包头（TTL、TOS、MARK等） PREROUTING、INPUT、FORWARD、OUTPUT、POSTROUTING
raw 绕过连接跟踪（NOTRACK） PREROUTING、OUTPUT
security 强制访问控制（SELinux 相关，较少使用） INPUT、FORWARD、OUTPUT

注：各表的链在 Netfilter hook 上按固定优先级顺序注册（如 raw → mangle → nat → filter），但同一 hook 上不同表的链是串行执行的，且规则按顺序匹配。

2、规则结构（Rule）

一条典型规则示例：

1iptables -t filter -A INPUT -s 192.168.1.100 -p tcp --dport 22 -m state --state NEW -j ACCEPT
  • -t filter：指定表；
  • -A INPUT：追加到 INPUT 链；
  • -s 192.168.1.100：源地址匹配；
  • -p tcp --dport 22：协议+目标端口匹配；
  • -m state --state NEW：使用 state 模块匹配连接状态；
  • -j ACCEPT：目标动作（ACCEPT、DROP、REJECT、LOG、自定义链等）。

3、匹配与动作机制

  • 匹配（Matches）：条件判断（如地址、端口、协议、状态、字符串、速率等），可组合（-m multiport --dports 22,80,443）；
  • 目标（Targets）：
    • 终止型：ACCEPT、DROP、REJECT（返回 RST/ICMP）；
    • 跳转型：JUMP 到用户自定义链（支持规则分组与复用）；
    • 扩展目标：LOG（记录日志）、NFLOG（发往 userspace）、REDIRECT（端口重定向）、MASQUERADE（动态 SNAT）等。

iptables 规则匹配与动作执行流程（单条链内）

当数据包到达某 hook 点（如 INPUT），内核按以下逻辑处理该链的规则：

  1. 顺序匹配：从链中第 1 条规则开始，逐条比对；
  2. 条件匹配：检查包的源/目的 IP、端口、协议、状态（conntrack）、接口、TCP 标志等是否满足规则条件；
  3. 匹配成功：
    • 若目标（target）为 ACCEPT / DROP / REJECT / LOG 等内置动作 → 立即终止该链匹配，执行对应动作（如丢弃或放行）；
    • 若目标为 自定义链 → 跳入该链继续匹配；返回后继续执行下一条规则（除非自定义链中明确 RETURN 或终止动作）；
    • 若目标为 SNAT / DNAT / MASQUERADE（仅在 nat 表特定链）→ 执行地址转换，并继续后续 hook 链（nat 表不终止流程，仅修改包）；
  4. 匹配失败：尝试下一条规则；
  5. 所有规则都不匹配 → 执行该链的 默认策略（policy）（如 iptables -P INPUT DROP）。

关键原则：

  • ACCEPT/DROP/REJECT 是终止动作（不继续后续规则）；
  • SNAT/DNAT 是修改动作，不终止匹配（但仅在 nat 表的 PREROUTING/OUTPUT/POSTROUTING 中生效）；
  • RETURN 用于从自定义链返回父链，继续执行父链的下一条规则。

运维与安全实践

  • 规则顺序至关重要：iptables 按链中规则从上到下顺序匹配，第一条匹配即执行对应动作（除非使用 -j CONTINUE 等特殊目标）。将高匹配频率规则（如 ESTABLISHED）放在链顶部；避免使用 -j LOG 在大量规则前（影响性能）；
  • 默认策略（Policy）：每条内建链有默认策略（ACCEPT 或 DROP），建议显式设置（如 iptables -P INPUT DROP），并确保管理通道（如 SSH）规则在前；
  • 状态化防火墙优势：结合 conntrack 和 -m state --state ESTABLISHED,RELATED -j ACCEPT，可安全放行返回流量，无需开放所有端口。或现代推荐的 -m conntrack --ctstate，依赖内核 nf_conntrack 模块，是高效防火墙的基础；
  • 持久化问题：iptables 规则重启后丢失，需通过 iptables-save / iptables-restore 或发行版工具（如 iptables-persistent、firewalld）保存；
  • 逐步迁移建议：Linux 内核 3.13+ 起，nftables 成为官方推荐替代方案（统一 IPv4/IPv6/ARP/bridge，语法更简洁，性能更优），但 iptables 仍广泛兼容（通过 iptables-nft 后端）。
  • 表与链的对应关系：
    • raw：绕过连接跟踪（NOTRACK）；
    • mangle：修改包头（TTL、TOS、MARK）；
    • nat：地址/端口转换（仅在 PREROUTING/OUTPUT/POSTROUTING）；
    • filter：核心过滤（INPUT/FORWARD/OUTPUT）；
    • security：SELinux/MAC 相关（较少使用）；
  • iptables 命令不实时处理包：iptables -A INPUT ... 仅向内核 netfilter 注册规则；包处理完全由内核在数据路径中完成，无用户态参与。

  • 流量限速与防攻击（limit、hashlimit 模块防暴力登录、CC）；
  • 日志审计（LOG 目标记录可疑连接）；
  • 透明代理/流量重定向（配合 REDIRECT 或 TPROXY）；
  • 容器/虚拟网络策略（如 Docker 默认使用 iptables 实现网络隔离）。

iptables 扩展

iptables 的匹配扩展（match extensions）是其强大功能的核心，它们通过 -m <module> 语法加载，用于在规则中实现更精细、更语义化的数据包匹配（如匹配端口范围、连接状态、字符串、IP 地址类型、速率、应用层特征等）。这些扩展由内核模块（xt_*）提供，需对应模块已加载（如 xt_tcp, xt_conntrack, xt_string 等）。

以下为 iptables（基于 Linux 内核 4.x–6.x 主流版本，兼容 iptables-nft 和 legacy 模式）中常用且稳定的核心匹配扩展的详细分类列表。

📌 注：所有扩展均作用于 filter、nat、mangle、raw、security 表中支持该扩展的链（如 INPUT、OUTPUT、FORWARD、PREROUTING、POSTROUTING），但并非所有扩展在所有表/链中都可用（例如 DNAT/SNAT 仅在 nat 表中有效，而 string 仅在 filter 表的 INPUT/FORWARD/OUTPUT 中常用）。

基础协议相关扩展（无需 -m，隐式加载）

这些是协议内置匹配项，不需显式 -m tcp 等，但实际由对应 xt_* 模块支撑：

协议 隐式匹配项 说明 示例
tcp --sport, --dport, --tcp-flags, --syn 等 匹配 TCP 头字段 iptables -A INPUT -p tcp --dport 22 -j ACCEPT
udp --sport, --dport 匹配 UDP 端口 iptables -A INPUT -p udp --dport 53 -j ACCEPT
icmp --icmp-type 匹配 ICMP 类型（如 echo-request） iptables -A INPUT -p icmp --icmp-type 8 -j ACCEPT
icmpv6 --icmpv6-type IPv6 ICMP 类型匹配 ip6tables -A INPUT -p icmpv6 --icmpv6-type 128 -j ACCEPT

提示：-p tcp 自动加载 xt_tcp 模块；同理 -p udp → xt_udp，-p icmp → xt_icmp。
