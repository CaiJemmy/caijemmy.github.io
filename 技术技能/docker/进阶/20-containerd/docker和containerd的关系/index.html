简单理解

Docker = 高级工具（用户友好的界面 + 额外功能）

containerd = 核心引擎（真正干活的）

runc = 底层执行器（创建容器进程）

历史演变

1. Docker 早期（2013-2016）

1Docker = 单体架构
2包含所有功能（构建、运行、网络、存储等）

2. Docker 拆分（2016）

Docker 把容器运行时部分捐献给 CNCF，成为独立项目 containerd：

1Docker Engine (dockerd)
2    ↓
3containerd  ← 独立项目，可单独使用
4    ↓
5runc  ← OCI 标准实现

3. 现在（2024+）

1Docker Engine = dockerd + containerd + runc

Docker 依赖 containerd，但 containerd 可以独立使用（不需要 Docker）。

实际调用关系

当你执行 docker run：

1docker run -d -p 8080:80 nginx:alpine

实际发生的事情：

 11. docker CLI 发送请求到 dockerd (Docker Engine)
 2   ↓
 32. dockerd 处理：
 4   - 解析参数（端口映射、网络配置等）
 5   - 创建网络和卷
 6   - 准备镜像
 7   ↓
 83. dockerd 调用 containerd API (gRPC)：
 9   "请帮我运行这个容器"
10   ↓
114. containerd 执行：
12   - 解压镜像层
13   - 准备 rootfs
14   - 创建容器配置
15   ↓
165. containerd 调用 runc：
17   "根据这个 OCI 配置创建容器进程"
18   ↓
196. runc 执行：
20   - 创建 namespace (pid, net, mount, etc.)
21   - 配置 cgroup (CPU、内存限制)
22   - 启动容器进程
23   ↓
247. 容器运行

验证它们的关系

查看进程树

1# 安装 pstree
2sudo apt install -y psmisc
3
4# 查看完整进程树
5pstree -p | grep -A 10 dockerd

你会看到类似：

1systemd(1)───dockerd(1234)───containerd(5678)───containerd-shim(9012)───nginx(9100)

查看 Docker 是否在使用 containerd

1# Docker 的 containerd socket
2ls -la /run/containerd/containerd.sock
3
4# Docker 守护进程信息
5docker info | grep -i containerd

输出：

1 containerd version: 1294c24a7da8e5a793ed378161673abe94118892
2 containerd: /run/containerd/containerd.sock

查看同一个容器在不同工具中

 1# 用 Docker 启动容器
 2docker run -d --name test-nginx nginx:alpine
 3
 4# 用 Docker 查看
 5docker ps
 6
 7# 用 ctr 查看（直接访问 containerd）
 8sudo ctr -n moby containers ls
 9
10# 用 crictl 查看（Kubernetes CRI 接口）
11sudo crictl ps

你会发现同一个容器在不同工具中都能看到，因为它们都是通过 containerd 管理的。

命名空间隔离

containerd 使用 namespace 来隔离不同调用者的容器：

1# Docker 使用的命名空间
2sudo ctr -n moby containers ls
3
4# Kubernetes 使用的命名空间
5sudo ctr -n k8s.io containers ls
6
7# 默认命名空间
8sudo ctr -n default containers ls

这就是为什么：

  • 用 docker ps 看不到用 ctr run 创建的容器
  • 用 ctr containers ls 看不到 Docker 容器（除非加 -n moby）

为什么 Kubernetes 弃用 Docker？

Kubernetes 需要的是 容器运行时，不需要 Docker 的额外功能：

 1┌────────────────────────────┐
 2│      Kubernetes             │
 3├────────────────────────────┤
 4│  之前：通过 dockershim      │
 5│    ↓                        │
 6│  Docker Engine (dockerd)    │  ← 多了一层，不需要
 7│    ↓                        │
 8│  containerd                 │  ← Kubernetes 真正需要的
 9└────────────────────────────┘
10
11┌────────────────────────────┐
12│      Kubernetes             │
13├────────────────────────────┤
14│  现在：直接使用 CRI         │
15│    ↓                        │
16│  containerd (CRI plugin)    │  ← 直接对接，更高效
17└────────────────────────────┘

结论：Kubernetes 弃用的是 dockershim（Docker 的包装层），不是 containerd。

什么时候用 Docker？什么时候用 containerd？

使用 Docker（dockerd + containerd）

✅ 适合场景：

  • 开发环境（需要 docker build、docker-compose）
  • 需要 Docker API 的工具（Portainer、Watchtower 等）
  • 需要简单的网络和卷管理
  • 团队熟悉 Docker 命令

❌ 不适合：

  • Kubernetes 生产环境（多余的开销）
  • 极简环境（只需要运行容器）

使用 containerd（纯 containerd）

✅ 适合场景：

  • Kubernetes 节点（生产环境）
  • 极简容器运行（嵌入式、IoT）
  • 需要更高性能和更低资源占用
  • 不需要 Dockerfile 构建

❌ 不适合：

  • 需要快速构建镜像（docker build）
  • 需要 Docker Compose 编排
  • 需要 Swarm 集群

工具选择

场景 推荐工具 命令示例
日常开发 Docker CLI docker run -d nginx
K8s 开发测试 nerdctl nerdctl run -d nginx
K8s 生产调试 crictl crictl ps
底层调试 ctr ctr -n k8s.io containers ls
镜像构建 Docker / Buildah docker build -t myapp .
容器编排 docker-compose / K8s docker-compose up -d

系统分析

从 docker version 输出：

1containerd:
2  Version:          v2.3.5
3  GitCommit:        1294c24a7da8e5a793ed378161673abe94118892
4runc:
5  Version:          1.5.1

说明：

  1. Docker Engine 29.8.0 依赖 containerd v2.3.5
  2. containerd 依赖 runc 1.5.1
  3. 系统完整链路：docker CLI → dockerd → containerd → runc → 容器

验证：

 1# 查看 Docker 使用的 containerd socket
 2docker info | grep containerd
 3
 4# 查看 Docker 容器（通过 containerd 的 moby 命名空间）
 5sudo ctr -n moby containers ls
 6
 7# 停止 Docker 守护进程后，containerd 仍然运行
 8sudo systemctl stop docker
 9sudo systemctl status containerd  # ← 仍在运行
10
11# 可以直接用 ctr 管理容器
12sudo ctr -n default run -d docker.io/library/nginx:alpine nginx-test

总结

  • Docker = 用户友好的高级工具，提供完整的开发体验
  • containerd = 核心容器运行时，负责实际的容器管理
  • runc = 底层执行器，按 OCI 标准创建容器

关系：Docker 调用 containerd，containerd 调用 runc

独立性：containerd 可以脱离 Docker 独立使用（Kubernetes 就是这样做的）

选择：

  • 开发环境 → 用 Docker（完整功能）
  • 生产 K8s → 用 containerd（高效精简）
  • 需要 Docker 兼容 + containerd 优势 → 用 nerdctl

工欲善其事，必先利其器。
